02 · Why this problem matters

A plausible postmortem is not causal evidence.

Long-horizon computer-use agents can fail dozens of steps after the first consequential mistake. Transcript-only debuggers can identify a suspicious step, but hidden state, irreversible actions, stale beliefs, and downstream policy choices make root-cause attribution underdetermined.

Failure is delayed

The action that makes success impossible can occur well before the visible failure. Final success hides the shape of the failure.

State is persistent

In software environments, one wrong edit can alter later observations and constrain every subsequent decision.

Diagnosis can sound right and still be wrong

If repairing the claimed root cause does not change the executed outcome, the explanation was not intervention-faithful.

03 · Core idea

Turn one failed trajectory into a controlled experiment.

TraceSurgery branches a failed run from multiple checkpoints, first verifying that the untouched continuation reproduces the source failure. It then applies preregistered interventions and replays the branch. The resulting counterfactual recovery surface reveals which intervention families can save the task, at which checkpoints, and when recovery becomes impossible.

Novelty boundary

TraceSurgery does not claim error taxonomies, critical-step localization, generic counterfactual repair, or minimal repair families as independently novel. The intended contribution is replay-controlled, checkpoint-indexed decomposition of recoverability across intervention families for stateful computer-use agents, plus an executed intervention-faithfulness test for diagnosis claims.

Research object

R(t, I) = task_success after intervention family I at checkpoint t

From this surface: last recoverable checkpoint, recovery AUC, diagnosis faithfulness, intervention-type decomposition, and an irreversibility frontier.

08 · Failure analysis

One executed failure, three different recovery mechanisms.

Initial state
raw = [10, 12, 20]Correct summary should be 42.
Step 0
Agent writes summary = 41Wrong action corrupts persistent spreadsheet state.
Step 1
Agent finishesFinal-state grader rejects the task.

Before the bad write — checkpoint 0

Action patch succeeds. Replacing 41 with 42 changes the executed outcome. Suffix replan also succeeds. A state reset alone fails because the unchanged suffix writes 41 again.

After the bad write — checkpoint 1

State patch succeeds. Correcting persistent spreadsheet state to 42 before the finish step saves the task. Replacing the finish action with itself or replaying the suffix cannot repair the already-corrupted state.

What this shows

The same failed run changes mechanism across time: before corruption, the causal lever is action/policy; after corruption, it is state. A single root-cause label loses this geometry.

Inside the research process

The polished story is not the whole story.

TraceSurgery did not move from idea → perfect implementation → amazing result. The evidence layer preserves the actual sequence: reproduce a failure, establish controls, try repairs that fail, revise the causal interpretation, tighten provenance, and only then expose the result.

9documented executed investigations
3failed repair attempts that changed the interpretation
8major design decisions with alternatives + trade-offs
4unexpected findings grounded in raw evidence
reproduce failure→replay control→action repair works→state repair fails→suffix repair works→move past corruption→action + suffix fail→state repair works→new mechanistic interpretation

What did not work

State repair at checkpoint 0 was overwritten by the next bad action. After corruption, changing only the terminal action or suffix was too late. Those negative branches are preserved rather than hidden.

Unexpected finding

The same failure changes repair mechanism across time: before corruption it is action/policy-recoverable; after corruption it becomes state-repairable. That observation motivates checkpoint-indexed intervention surfaces.

11 · Safety / limitations

Recovery is not always desirable—or possible.

Irreversible actions

Some sends, deletes, payments, submissions, or external side effects cannot be safely “replayed away.” These require environment-specific containment and must be labeled non-recoverable rather than silently reset.

Permission boundaries

Privileged evaluator state is allowed for causal probes but must never leak to deployable agent baselines. Oracle surgery is an upper-bound instrument, not an agent capability.

Human escalation

High-risk or ambiguous recovery paths should terminate or escalate rather than optimize task success through unsafe actions. Safety events are retained in evaluation.

Main limitations: realistic environment nondeterminism, coverage of intervention families, hidden confounding outside recorded state, oracle repair realism, and external-study cost. See Safety and Project Status.
